## 1. Падение сайта (503)

### Что происходило

Университетский балансировщик `192.168.21.49` опрашивает сервер запросом
`OPTIONS / HTTP/1.0` каждые 5 секунд и ждёт `200`. Конфигурация nginx,
установленная 14 октября, добавила `return 301` на корне. Проверки начали
падать, **последняя успешная записана 15 октября в 07:13**, после чего
балансировщик выбросил сервер из пула — отсюда и 503 у посетителей.

### Что сделано

В `deploy/nginx-find-uz.conf` корень обрабатывается отдельно:

```nginx
location = / {
    if ($request_method = OPTIONS) {
        return 200 "";
    }
    proxy_pass http://127.0.0.1:3000;
}
```

Next.js на `OPTIONS` отвечает `405`, поэтому ответ формирует сам nginx.
Редирект с 80 на 443 убран: он указывал обратно на балансировщик и давал
петлю. Слушаются порты 80, 443 и 4443.

### Ошибки, которые я допустил по дороге

Первая гипотеза была неверной: я решил, что балансировщик ходит напрямую на
`192.168.20.21:3000`, и что виновата привязка Next.js к `127.0.0.1`. Вывод
`diagnose.sh` это опроверг — ufw пропускает только 22/80/443/4443 при
`default deny`, то есть порт 3000 снаружи не был доступен никогда. Привязку
вернул на loopback.

Проверял я тоже неправильно: через `127.0.0.1` и через записи в `/etc/hosts`,
которые ведут оба домена на `127.0.1.1`. Это обходит реальный путь запроса
целиком, поэтому мои «проверки» ничего не доказывали. Дальше всё
перепроверялось через `curl -k https://127.0.0.1/ -H 'Host: lugat.uwed.uz'` —
тот же путь, которым идёт посетитель.

### Осталось на стороне университета

Файл `deploy/ЗАПРОС_СЕТЕВИКАМ.txt`: сетевая служба должна подтвердить, какой
порт они опрашивают, оставить `192.168.20.21` в пуле и сказать, кто
терминирует TLS.

## 2. Почему словарь был пустым

### Причина первая: пагинация DRF

`DiplomaticTermView` наследовал общий `PageNumberPagination` (PAGE_SIZE 50) и
отдавал `{"count":…, "next":…, "results":[…]}`. Клиент в
`src/app/dictionary/DictionaryClient.tsx:66` делает:

```ts
if (!Array.isArray(terms)) return {};
```

Объект — не массив, проверка молча возвращала пустую группировку, страница
рисовала «ноль терминов». Ни одной ошибки в консоли.

**Исправлено:** `pagination_class = None` на `DiplomaticTermView`. Страница
группирует термины по буквам в браузере, поэтому ей нужен весь список
сразу; сериализатор узкий и `.only()` пропускает тяжёлое поле `definition`,
так что все 1190 строк — это около 140 КБ.

Та же ошибка позже найдена у `CategoryView` — исправлена так же.

### Причина вторая: пять отсутствующих эндпоинтов

Клиент годами вызывал адреса, которых на бэкенде не было. Все отвечали `404`:

| Эндпоинт | Кто вызывает |
| --- | --- |
| `/dictionary/search_term/` | поиск |
| `/dictionary/term_detailed/<id>/` | страница термина |
| `/dictionary/term_photo/<id>/` | фотография термина |
| `/dictionary/country/` | связанные страны |
| `/dictionary/source/` | источники |

**Исправлено:** добавлены `SearchDiplomaticTermView`,
`DiplomaticTermDetailedView`, `TermPhotoView`, `CountryView`, `SourceView`.
Данные и сериализаторы уже существовали — не хватало только представлений и
записей в роутере.

## 3. Админка была недоступна

`/admin` отправлял на `https://localhost:3000/admin/login` — посетителя
выбрасывало с сайта.

```ts
return NextResponse.redirect(new URL("/admin/login", request.url));
```

Внутри middleware `request.url` содержит адрес, на котором слушает сам
Next.js (`127.0.0.1:3000`), а не имя, которое набрал посетитель. Схема при
этом получалась `https` из `X-Forwarded-Proto`, поэтому результат выглядел
почти правильным и сбивал с толку.

**Исправлено:** адрес собирается из `X-Forwarded-Host` и `X-Forwarded-Proto`,
которые проставляет nginx.

Промежуточная попытка — вернуть относительный `Location` — дала `500` на всех
маршрутах админки: Next.js разбирает заголовок как URL и требует абсолютный
(`ERR_INVALID_URL`). Это зафиксировано здесь, чтобы не повторять.

Удалён `src/app/internal-api/middleware.ts` — мёртвый файл (Next.js грузит
только корневой middleware) с копией той же ошибки.

## 4. Вход в админку: «перезагружает и ничего не понятно»

```ts
if (error.response?.status === 401) { window.location.href = "/admin/login"; }
```

Перехватчик ответа в `src/lib/apiClient.ts` отправлял браузер на страницу
входа при **любом** `401` — включая тот `401`, который и есть ответ сервера
«неверный пароль». Страница перезагружалась раньше, чем React успевал
показать сообщение, форма очищалась, пользователь не видел ничего.

**Исправлено:**

- маршруты `/auth/token`, `/auth/token/refresh`, `/auth/token/verify`
  исключены из этой логики — там `401` это ответ, а не истёкшая сессия;
- редирект срабатывает только изнутри панели и не на странице входа;
- разные сообщения: неверный пароль, истёкшая сессия, нет сети, сбой сервера;
- кнопка показа пароля, блокировка формы на время отправки;
- `AdminAuthGuard` больше не уничтожает сессию, когда сервер просто
  недоступен, и не пишет токены в консоль браузера.

## 5. Форма обратной связи

### Она не работала вообще

Форма отправляла на `/internal-api/contact`, который пересылал на
`${BACKEND_URL}/dictionary/contact/`. Этого эндпоинта на бэкенде не было, как
и модели. **Каждое отправленное сообщение терялось.**

**Сделано:**

- модель `Contact` (миграция `0007_contact`) с полем `is_read`;
- `ContactView` — публичный `POST /dictionary/contact/`;
- `ContactAdminView` — список, чтение (с отметкой «прочитано»), изменение и
  удаление под `/dictionary/contact_admin/`;
- маршрут `src/app/api/contact/route.ts` — секрет reCAPTCHA и ограничение по
  IP остаются на сервере; адрес Django наружу не отдаётся.

### reCAPTCHA отдавала 403

После запуска форма стала отвечать `403 «Bu amal uchun ruxsat yoʻq»`, а Google
показывал в углу страницы ошибку.

Ключи в `.env.local` — это ключи **reCAPTCHA v2**, а код вызывает
`grecaptcha.execute(siteKey, { action })` — это API **v3**. Браузер отвечал
«Invalid site key type», наружу уходил негодный токен, Google его отклонял.

**Сделано:** оба ключа очищены, форма работает без капчи под ограничением
5 сообщений в час с одного IP. Инструкция по получению ключей v3 —
`deploy/README.md`. Старые ключи лежат в истории git, их нужно отозвать в
консоли Google, а не просто заменить.

### Поведение капчи сделано отказоустойчивым

Если Google недоступен или ключ не того типа, сообщение всё равно уходит, но
под уменьшенной квотой (2 в час). Отклоняется только токен, который Google
активно забраковал. Молчащая форма обратной связи хуже, чем форма без капчи.

### Вёрстка

Поля шли одной колонкой и «слипались». Имя и почта теперь в одной строке,
блок согласия вынесен в отдельную рамку, мелкий текст перенесён к кнопке,
добавлен счётчик символов.

## 7. Загруженные фотографии не отдавались

`core/urls.py` подключал медиа через `static(MEDIA_URL, …)`, а эта функция
**превращается в пустоту при `DEBUG = False`**. На продакшне любой загруженный
файл отвечал `404`. Каталога `media/` не существовало вовсе.

Вдобавок DRF строил URL фотографии от хоста входящего запроса. Next.js
рендерит страницы на сервере через `127.0.0.1:8000`, поэтому в публичный HTML
уходил **реальный адрес бэкенда**, а картинка была недоступна снаружи. Это
прямо запрещено правилом 1 в `CLAUDE.md`.

**Сделано:**

- `core/urls.py` отдаёт каталог явно через `django.views.static.serve`;
- `RelativeImageField` возвращает `/media/...` — относительный путь,
  который разрешается от домена посетителя;
- `src/app/media/[...path]/route.ts` отдаёт файл под публичным доменом,
  с защитой от обхода каталога и белым списком типов;
- создан `backend/media/images/terms/`.

Правильное долгосрочное решение — `location /media/` в nginx (нужен sudo),
снимок конфигурации в `deploy/README.md`. После этого маршрут Next.js просто
перестанет получать запросы.

## 8. Обработка ошибок и слабой связи

Раньше любая неудача показывалась строкой вида
`Request failed with status code 500` — на узбекской странице, по-английски.

Сделано:

- `ApiError` получил поле `kind`: `offline | network | timeout | unauthorized
  | forbidden | notFound | rateLimited | server | client`;
- `src/lib/apiErrors.ts` — `apiErrorMessage()` превращает любую ошибку в
  фразу на языке читателя; служебные строки axios отфильтровываются;
- `GET`-запросы повторяются до трёх раз с нарастающей паузой; в офлайне не
  ждут впустую;
- тайм-аут поднят с 10 до 25 секунд — десяти не хватало мобильной связи;
- `src/hooks/useNetworkStatus.ts` и `NetworkStatusBanner` — тихая строка
  «нет связи», ничего не блокирует;
- `src/components/ui/ErrorState.tsx` — единая панель ошибки; кнопка повтора
  появляется только там, где повтор может помочь (на `404` её нет);
- границы ошибок для `/dictionary` и `/admin`, плюс `global-error.tsx` без
  провайдеров и MUI — на случай падения самого корневого layout;
- неудачное обновление больше не стирает словарь, который человек читает:
  показывается уведомление, список остаётся.

### Пустой экран на главной

```html
<div className="relative min-h-screen">   <!-- src/app/page.tsx -->
```

Корневой layout — это уже `min-h-screen` flex-колонка, где `<main>` имеет
`flex-1`. Главная резервировала **второй** полный экран, отсюда дыра до
футера на ПК и на телефоне. Убрано. Так же снят `pt-[128px]` на странице
термина — отступ под шапку, которая `sticky`, а не `fixed`.

### Поиск терялся при возврате

Запрос жил только в переменной модуля, в адресе его не было. После перехода
на термин кнопка «Назад» возвращала несортированный словарь. Теперь запрос
хранится в `?q=`, восстанавливается при открытии и при каждом
`popstate`. Условие `window.history.length > 2` в кнопке возврата заменено на
`> 1`: когда словарь был первой страницей вкладки, длина равна 2 и возврат
не срабатывал.

Сделано через `window.history`, а не `useSearchParams`: страница словаря
рендерится статически, и хук перевёл бы её в динамический режим ради
клиентской мелочи.

`backend/.gitignore` был в кодировке **UTF-16LE с CRLF**, поэтому git не читал
из него ни одного правила. Отсюда 30 закоммиченных `.pyc` и неигнорируемые
`.venv` и `.env`. Перекодирован в UTF-8/LF, мусор убран из индекса.

Ветки фронтенда проверены:

| Ветка | Состояние |

| `claude-legal-audit` | уже влита в `new` |

`release-prep-frontend` мерджить нельзя: она старше текущей ветки и слияние

уже перенесено более поздними коммитами.

### Конфигурация

- `DJANGO_SECRET_KEY` не был задан — Django генерировал случайный ключ при
  каждом перезапуске, что обнуляло все выданные JWT. Зафиксирован в `.env`.
- `DEBUG = True` на продакшне — отладочные страницы `404` показывали публике
  все маршруты. Выключено.
- `SECURE_SSL_REDIRECT` оставлен `False` осознанно: Next.js ходит в Django по
  `http://127.0.0.1:8000` без `X-Forwarded-Proto`, и `True` разворачивал бы
  каждый внутренний вызов в `301`.
- `HSTS = 0`, пока сертификат самоподписанный: иначе браузер уберёт кнопку
  «всё равно перейти».
- `frontend/.env.local` содержал `BACKEND_URL=https://dip-lugat.uz/api` —
  Node.js ходил наружу через nginx в самоподписанный сертификат, который он
  отказывается проверять. Заменено на `http://127.0.0.1:8000`.
- `ecosystem.config.js` переписан; в старом был `PATH: "…:$PATH"`, который
  PM2 никогда не разворачивает.
- По одному воркеру на процесс осознанно: без `REDIS_URL` используется
  `LocMemCache`, и второй воркер uvicorn вёл бы собственные счётчики
  ограничения запросов.

### Диск

Был занят на 93% — 690 МБ свободно. Очищены кэш npm, кэши uv и pip, кэш
сборки Next.js (`.next/cache`, 378 МБ, нужен только для ускорения следующей
сборки). Стало 85%, 1,5 ГБ свободно.

Ещё 1,2 ГБ в `/var/log`, но туда нужен sudo:
`sudo journalctl --vacuum-size=200M`.

### Docker

Заброшенный стек в `lugat/` пробрасывает порты 80 и 443. Контейнер
`lugat-app-1` крутился в цикле перезапуска; владелец остановил его и снял
автозапуск. **Любой `docker compose up` в этом каталоге отнимет порты у
системного nginx** — ровно то, что показывают ошибки `bind() … Address
already in use` от 14 октября.

3. **Четыре разных апострофа** в заголовках: `ʻ` U+02BB — 30 раз, `'` — 197,
   `'` — 23, `'` — 1. Правильный для `Oʻ`/`Gʻ` только первый. Сортировка это
   переживает (`uzbekCollation` приводит варианты к одному), но любая
   машинная обработка текста споткнётся.
